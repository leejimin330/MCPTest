# 설계 — 부화소 (2026-08-16)

**상태:** 설계 승인됨. 구현 전.
**전제:** `2026-08-15-shop-design.md` 에서 이어진다. 그 문서 7절이 "부화소 / 알을 깨는 것"을
다음 작업으로 미뤄 뒀고, HANDOFF 4.3 의 남은 절반(**산 알을 어떻게 쓰는가**)을 여기서 닫는다.

상점에서 알을 살 수 있게 됐지만 **깰 방법이 없다.** 산 알은 인벤토리에 `egg_sprigling`
키로 쌓이기만 하고, `EggData.hatchesInto` 를 읽는 코드가 한 줄도 없다.
부화소 건물(x −6)은 서 있지만 패널이 없어 클릭하면 "알 시스템 준비 중" 로그만 뜬다.

이 문서는 그 루프를 닫는 부화소의 설계다. **재화 → 알 → 새 케어**가 이어지면
전투로 번 것이 육성으로 돌아오는 바깥 순환이 완성된다.

---

## 1. 확정된 결정

| 항목 | 결정 |
|---|---|
| 부화 방식 | **즉시 부화.** [부화]를 누르면 그 자리에서 알이 사라지고 케어가 나온다 |
| 헛간이 가득 찰 때 | **거부.** 알도 그대로 남는다. 버튼을 죽이지 않는다 |
| 부화한 케어 | **헛간(보유 목록)까지만.** 파티 합류는 헛간에서 따로 한다 |
| 규칙이 사는 곳 | **`HatchService` 신설.** 상점의 `ShopService` 와 같은 자리 |
| 세이브 | **v3 그대로.** 포맷을 바꾸지 않는다 |
| 씬 | 패널 1종 추가 → `careManager.panels` 5개 → **6개** |

### 1.1 즉시 부화인 이유

품기 카운터("N번 돌봐야 깨진다")나 전투 N회 조건은 **"품는 중인 알"이라는 새 상태**를
만든다. 그 상태는 세이브에 들어가야 하므로 v3 → v4 가 되고, 부화소 패널은 알 목록과
품는 중 목록 두 가지를 그리게 된다.

지금 게임에는 시간 경과 개념이 아예 없다 — 먹이도 훈련도 누르는 즉시 끝난다.
부화만 대기를 갖는 것은 이 게임의 결에 맞지 않는다. **구매와 같은 즉발 동작**으로 둔다.

품기를 나중에 넣더라도 `HatchService.TryHatch` 는 "조건이 찼을 때 부르는 함수"로
그대로 남는다. 지금 결정이 나중을 막지 않는다.

### 1.2 헛간이 가득 찰 때 버튼을 죽이지 않는 이유

다른 패널이 전부 **"누르면 거부 로그"** 방식이다 — 포만도가 모자란 훈련도, 재화가
모자란 구매도 버튼은 살아 있고 눌러야 이유를 알려준다. 부화만 회색 버튼을 쓰면
혼자 다른 규칙이 되고, 버튼 상태를 매 `Refresh` 마다 계산해야 한다.

대신 **제목에 `헛간 3/8` 을 상시로 띄운다**(5절). 거부되는 유일한 이유가 자리이므로,
누르기 전에 보이는 편이 회색 버튼보다 정보가 많다.

### 1.3 파티에 자동 합류시키지 않는 이유

파티 편성은 헛간 패널의 책임이다. 부화가 `Roster.Add` 와 `Roster.JoinParty` 를
연달아 부르면, **둘째가 실패해도(파티 4마리 만석) 부화는 성공인** 어중간한 결과를
`ActionResult` 하나로 표현해야 한다. 메시지가 "나왔다. 그런데 못 나갔다"가 된다.

`Roster.Add` 하나로 끝내면 그 문제가 없다. 갓 난 케어를 필드에서 보려면 헛간에서
한 번 더 누르면 된다 — 헛간은 이미 그 일을 한다.

### 1.4 세이브를 안 건드리는 이유

부화가 바꾸는 것은 **인벤토리의 알 개수**와 **로스터의 케어 목록** 둘뿐이고,
v3 는 이미 양쪽을 저장한다(보유 배열 + 인벤토리 id/개수). 새로 생기는 상태가 없으므로
포맷이 그대로다. 1.1 에서 품기를 버린 대가로 얻는 이득이 이것이다.

## 2. 코어 — `HatchService`

```csharp
namespace FarmCreature.Core
{
    public static class HatchService
    {
        public static ActionResult TryHatch(GameState state, EggData egg);
    }
}
```

`ShopService` 와 같은 자리·같은 성격이다. `EggData`(ScriptableObject)를 인자로 받는 것은
`CareActions.Equip(ItemData)` 와 같은 방식이고, EditMode 테스트는
`ScriptableObject.CreateInstance<EggData>()` 로 에셋 없이 돈다.

### 2.1 규칙 — 검사를 전부 끝낸 뒤에 소모한다

1. `state` · `state.Inventory` · `state.Roster` · `egg` · `egg.eggId` · `egg.hatchesInto`
   중 하나라도 없으면 → 실패 `"부화시킬 수 없는 알이다."`
2. `Inventory.GetCount(egg.eggId) < 1` → 실패 `"가진 알이 없다."`
3. `state.Roster.IsFull` → 실패 `"헛간이 가득 찼다. (최대 8마리)"`
4. `Inventory.TryConsume(egg.eggId, 1)`
5. `CreatureInstance.CreateNew(egg.hatchesInto)` → `state.Roster.Add(...)`
6. 성공 `"스프리글링 알에서 스프리글링이 나왔다."`

**2·3번을 4번보다 앞에 두는 것이 이 설계의 핵심이다.** 부화는 인벤토리와 로스터
**두 곳**을 건드리므로 절반만 적용된 상태(알은 사라졌는데 케어는 없음)가 실재하는 위험이다.
두 전제를 먼저 확인했으므로 5번의 `Roster.Add` 는 실패할 수 없다 —
새 인스턴스라 중복이 아니고, 자리도 방금 확인했다.

상점은 "차감 먼저, 지급 나중"으로 같은 보장을 얻었다(`TrySpendGold` 가 실패 시 아무것도
바꾸지 않으므로). 부화는 소모 전에 지급 가능 여부를 확인할 수 있어 순서가 반대다.
**보장은 같다: 실패하면 아무것도 바뀌지 않는다.**

### 2.2 `hatchesInto` 가 비어 있으면 거부한다

`CreatureInstance.CreateNew(null)` 은 `ArgumentNullException` 을 던진다. 그 전에 막아
`ActionResult` 실패로 돌린다. 가격 0 을 거부하는 `ShopService` 와 같은 판단이다 —
**데이터 실수를 조용히 넘기지 않되, 예외로 게임을 죽이지도 않는다.**

## 3. 표시 문자열 — `PanelLabels`

```csharp
public static string HatchTitle(GameState state);   // "부화소   헛간 3/8"
public static string HatchRow(EggData egg, int owned);  // "스프리글링 알   보유 2   →  스프리글링"
```

`egg == null` 이면 `"(빈 칸)"` — `ShopRow` 와 같다.

행에 부화 결과 종을 같이 쓰는 이유: `egg.hatchesInto` 를 이미 들고 있고,
**뭐가 나오는지 모르고 깨는 것은 이상하다.** 알 종류가 늘면 이 칸이 유일한 구분점이 된다.

## 4. 화면 — `HatchPanel`

`GamePanel` 을 상속한다. `ShopPanel` 과 같은 뼈대다 — 규칙은 `HatchService` 한 곳에 있고
패널은 표시와 배선만 한다.

```
┌─ 부화소   헛간 3/8 ──────────────────────────┐   900×420
│                                              │
│  스프리글링 알   보유 2  →  스프리글링   [ 부화 ]  │
│                                              │
│                  [ 닫기 ]                     │
└──────────────────────────────────────────────┘
```

- 행은 `EggDatabase.eggs` 인덱스와 **1:1**, 개수는 씬 생성 시점에 고정된다(함정 3.1)
- `[부화]` 버튼은 **int 인자 persistent listener** 로 인덱스를 넘긴다(함정 3.6)
- 보유 0 이어도 버튼은 살아 있다. 누르면 `"가진 알이 없다."` (1.2)
- 패널 크기 **900×420**. 상점(620)보다 낮춘 이유는 알이 1종이라 620 이면 텅 비기 때문이다.
  **알이 4종을 넘으면 이 숫자를 올려야 한다** — 상점도 같은 제약을 갖는다

**참조**(`GameBootstrap` 이 채운다)

| 필드 | 쓰임 |
|---|---|
| `eggDatabase` | 행 개수와 알 정보 |
| `careManager` | 로그 출력과 `RefreshAll` |
| `titleText` / `rowTexts` | 표시 |

**부화 성공 후 `careManager.RefreshAll()`** — 헛간 패널의 보유 줄과 부화소 제목의 `3/8` 이
같이 바뀌어야 한다. 실패해도 부른다(상점과 같다). 로그는 `CareManager.SetLog`.

## 5. 씬 배선 (`GameBootstrap`)

- `BuildHatchPanel(panelRoot.transform, careManager, eggDb)` 추가
- `careManager.panels` 에 넣어 **6개**
- 건물↔패널 `switch` 에 `case BuildingKind.Hatchery: → hatchPanel` 추가 (지금은 분기가 없다)
- 배선이 전부 끝난 **뒤에** `SetActive(false)` — 패널 6종 전부 닫고 저장(함정 3.8)
- 행 개수가 0 이면 `Debug.LogError` — **0 은 정상 상황이 아니라 참조가 죽었다는 뜻이다**
  (함정 3.9/3.10). `eggDb` 는 `NewScene` 이후 재로드된 것을 써야 한다

`FarmBuilding.cs` 의 안내 문구에서 `"(알 시스템 준비 중)"` 을 뗀다.

**씬 재생성이 필요하다** — `BuildAll` 을 돌려야 행과 버튼이 생긴다.

전투 씬 전용이고, 부화는 농장 씬 안에서 끝난다. 회귀 확인용으로 돌리기만 한다.

### 6.4 실행 순서

1. EditMode 테스트를 먼저 올린다 (`HatchService` 가 없으므로 컴파일 실패 → 구현 → 통과)
2. `SceneIntegrityCheck` 를 6종·5동으로 올린다 — **검사가 실패하는 것을 눈으로 확인**
3. `BuildAll` 재실행 → 무결성 검사 통과 확인
4. EditMode 전량 → PlayMode 스모크 전량

셋 다 **Unity 에디터를 닫고** 돌린다(함정 3.5). **종료 코드만 믿지 않는다** —
생성된 씬을 직접 확인한다.

## 7. 범위 밖

- **품기·부화 대기 시간** — 1.1
- 알에서 스프리글링 외의 종이 나오는 것 (알이 1종뿐이다)
- 전투 드랍이나 헛간 번식으로 알을 얻는 것 (상점 구매가 유일한 경로다)
- 케어 방출/삭제 — 헛간 8마리가 차면 부화가 영구히 막힌다. 8절 참고
- **`GameRoot.startingCreatureCount` 를 3 → 1 로 줄이는 것.** 코드에 "부화소가 생기기
  전까지의 임시 조치"라 적혀 있지만, 줄이면 **새 게임 시작 시 재화 0 → 알을 못 삼 →
  파티를 못 채움**이 되어 시작 재화 밸런스까지 함께 봐야 한다. 밸런스를 따로 잡을 때 처리한다
