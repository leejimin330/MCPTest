# 설계 — 전투 화면 (2026-08-14)

**상태:** **구현 완료 (2026-08-14).** 구현 계획과 실행 기록은
`docs/superpowers/plans/2026-08-14-battle-screen.md` 에 있다.
**전제:** `2026-08-13-battle-and-roster-design.md` 에서 이어진다.

> **설계에서 벗어난 두 곳(의도적):**
> 1. 체력바를 uGUI `Image` 가 아니라 `SpriteRenderer` 로 만들었다 (4.1). 월드 좌표에 uGUI 를 붙이려면
>    World Space Canvas 라는 새 장치가 필요한데, 농장이 이미 건물 이름표를 `TextMesh` 로 처리하고 있어
>    같은 방식을 따랐다. 덤으로 무결성 검사 1번이 체력바까지 덮는다.
> 2. `BattleResult` 가 `GameState` 를 함께 나른다 (3.2에 없던 것). 없으면 농장 씬이 다시 로드될 때
>    `GameRoot` 가 세이브를 읽어 **저장 전 진행이 전부 날아간다.**

지금 전투터는 텍스트 두 덩어리(진영 목록 + 로그)뿐이다. 캐릭터도 체력바도 연출도 없다.
이 문서는 그것을 실제 전투 화면으로 바꾸는 설계다.

---

## 1. 확정된 결정

| 항목 | 결정 |
|---|---|
| 전투가 벌어지는 곳 | **별도 전투 씬.** 농장 → 전투 씬 전환 → 끝나면 농장 복귀 |
| 플레이어 조작 | **관전만.** 배속(1x/2x)과 나가기 버튼뿐 |
| 시점 | **탑뷰 맵.** 단 캐릭터는 농장과 동일한 **옆모습 스프라이트** |
| 적 배치 | 인카운터에 **설정해 둔 영역 안의 랜덤 좌표**에서 스폰 |
| 위치의 역할 | **표시 전용.** 전투 규칙은 좌표를 보지 않는다 |
| 데이터 편집 | 적·인카운터·맵 에셋은 **인스펙터 편집을 보존**한다 (seed-only) |

### 1.1 이 조합이 중요한 이유

위치를 표시 전용으로 두기로 한 것이 이번 설계에서 제일 큰 절약이다.

`BattleSimulator` 는 **난수를 쓰지 않는** 순수 C# 이고, 그 덕에 EditMode 테스트 13개가
시간을 흘려보내며 결과를 단언할 수 있다. 만약 이동·사거리를 규칙에 넣었다면 시뮬레이터를
다시 쓰고 그 테스트도 전부 재작성해야 했다.

**스폰 좌표는 랜덤이지만 전투 결과는 여전히 결정적이다** — 규칙이 좌표를 읽지 않기 때문이다.
`BattleSimulator` 와 `BattleUnit` 은 **한 줄도 바뀌지 않는다.** 이번 작업은 전부 Presentation
과 Data 계층이다.

> **나중에 이동·사거리를 넣고 싶어지면** 그때는 이 결정을 뒤집는 별도 설계가 필요하다.
> "지금 좌표만 넣어두고 나중에 규칙에 연결하자" 는 유혹은 거절한다 — 규칙이 좌표를 읽는
> 순간 결정성이 깨지고, 그건 화면 작업이 아니라 코어 작업이다.

## 2. 데이터

### 2.1 새 ScriptableObject 3종

```
BattleMapData          바닥 크기·색, 아군 스폰 영역, 적 스폰 영역
BattleEncounter        표시 이름, 등장 적 목록(수 포함), 쓸 맵
BattleEncounterDatabase 전투터에 뜨는 인카운터 목록  ← 버튼 개수가 여기서 나온다
```

**`BattleMapData`**

| 필드 | 뜻 |
|---|---|
| `displayName` | 맵 이름 |
| `groundSize` | 탑뷰 바닥의 가로·세로 (월드 유닛) |
| `groundColor` | 바닥 색 (플레이스홀더) |
| `allySpawnArea` | 아군이 설 사각 영역 (중심 + 크기) |
| `enemySpawnArea` | 적이 설 사각 영역 |
| `minSpacing` | 유닛끼리 최소 간격. 겹쳐 서는 것을 막는다 |

**`BattleEncounter`**

| 필드 | 뜻 |
|---|---|
| `displayName` | 전투터 버튼에 뜰 이름 (예: "들판 — 들쥐 떼") |
| `entries` | `{ EnemyData enemy; int count; }` 목록 ← **"적의 수" 는 여기서 편집** |
| `map` | 쓸 `BattleMapData` |

적 총원은 `entries` 의 `count` 합이다. 상한은 `BattleField.MaxEnemies`(아래 4.3).

### 2.2 편집 보존 — seed-only

지금 `GameBootstrap.LoadOrCreate<T>` 는 기존 에셋을 불러온 **뒤 필드를 전부 덮어쓴다.**
그래서 인스펙터에서 고친 값이 다음 `BuildAll` 에 사라진다.

전투 데이터에는 새 헬퍼를 쓴다:

```csharp
/// 없으면 만들어 초기값을 넣고, 이미 있으면 손대지 않는다.
/// 반환값의 두 번째가 true 면 이번에 새로 만든 것이다.
private static T LoadOrSeed<T>(string assetPath, out bool created) where T : ScriptableObject
```

**적용 범위를 전투 데이터로 한정한다** — `EnemyData` · `BattleMapData` · `BattleEncounter` ·
`BattleEncounterDatabase`. 종·아이템·씬은 지금처럼 코드가 전권을 쥔다.

근거: 손으로 밸런스를 만지는 대상은 전투뿐이다. 전면 seed-only 로 바꾸면 "씬과 에셋은
언제든 재생성 가능해야 한다"(PRD N5)가 약해진다. 경계를 전투에 그으면 두 요구가 다 산다.

> **대가:** 전투 데이터의 초기값을 바꿔도 기존 에셋에는 반영되지 않는다.
> 초기값을 다시 깔려면 해당 에셋을 지우고 `BuildAll` 을 돌려야 한다. 이 사실을 HANDOFF 에 적는다.

## 3. 씬 전환과 상태 전달

### 3.1 문제

`GameState`(보유·파티·재화·대상)는 지금 농장 씬 안에서만 산다. 씬을 바꾸면 사라진다.

### 3.2 `BattleHandoff` — 순수 C# 정적 전달자

```
농장 씬                          전투 씬
  BattleHandoff.Request = {          →   꺼내서 전투를 차린다
    GameState, BattleEncounter }
  SceneManager.LoadScene("Battle")

  결과를 읽어 재화 반영         ←        BattleHandoff.Result = {
  SceneManager.LoadScene("Farm")          Outcome, GoldReward }
```

`DontDestroyOnLoad` 싱글턴 대신 정적 클래스를 쓰는 이유: `GameState` 는 이미 순수 C# 이라
`MonoBehaviour` 에 실어 나를 이유가 없고, 정적 전달자는 EditMode 에서 그대로 테스트된다.

**전투 씬을 단독으로 Play 했을 때**(`Request` 가 비었을 때)는 오류로 죽지 않고
**연습용 더미 인카운터**로 시작한다. 개발 중 전투 씬만 열어보는 일이 잦기 때문이다.
이 폴백은 로그로 분명히 알린다.

### 3.3 재화는 농장에서 반영한다

전투 씬은 `GameState` 를 **읽기만** 하고 재화를 직접 더하지 않는다.
승패와 보상액만 `Result` 에 담고, 농장으로 돌아온 뒤 농장 쪽이 `AddGold` 를 부른다.

이렇게 나누는 이유: 전투 씬이 중간에 죽거나 사용자가 강제로 씬을 바꿔도
재화가 이중으로 들어가지 않는다. 지급 지점이 한 곳뿐이다.

## 4. 화면

### 4.1 구성

```
┌────────────────────────────────────────────┐
│                                            │   탑뷰 바닥
│      ●                        ▲            │   아군은 왼쪽 영역
│   ●        ●              ▲       ▲        │   적은 오른쪽 영역의
│      ●                        ▲            │   랜덤 좌표
│                                            │
├────────────────────────────────────────────┤
│  스프리글링 → 들쥐 평타 8                    │   로그 (최근 몇 줄)
│  들쥐 쓰러짐.                                │
│                        [1x] [2x] [나가기]   │
└────────────────────────────────────────────┘
```

- 바닥은 탑뷰 평면이지만 **캐릭터는 옆모습**이다 — 농장과 같은 `Circle.png` 에
  종·적의 `placeholderColor` / `placeholderScale` 을 입힌다. 아군은 오른쪽,
  적은 왼쪽을 보도록 `flipX` 를 준다.
- 유닛마다 머리 위에 **이름 + 체력바**. 체력바는 `Square.png` 를 가로로 늘린 Image 두 장
  (바탕 + 채움)으로 만든다. **런타임 생성 스프라이트를 쓰지 않는다**(함정 3.1).
- 쓰러진 유닛은 반투명으로 흐려 두고 지우지 않는다. 갑자기 사라지면 무슨 일이 났는지 안 보인다.

### 4.2 배속과 종료

`BattleSimulator.Tick(dt)` 에 `Time.deltaTime * speed` 를 넘긴다. 시뮬레이터가 시간을
바깥에서만 받으므로 **배속은 공짜로 얻어진다.** 1x / 2x 두 단계만 둔다.

[나가기]는 전투 중에도 누를 수 있다. 진행 중에 나가면 **보상 없음**으로 처리한다
(`Result.Outcome = Aborted`). 도망 페널티는 두지 않는다 — 지금은 져도 잃는 것이 없는 게임이다.

### 4.3 스폰 — 랜덤이되 겹치지 않게

```csharp
/// 영역 안에서 서로 minSpacing 이상 떨어진 좌표를 count 개 고른다.
/// 시도 횟수 상한을 두고, 못 채우면 격자로 물러난다 (무한 루프 방지).
public static List<Vector2> PickSpawnPoints(Rect area, int count, float minSpacing, int seed)
```

**순수 함수로 분리해 EditMode 로 검증한다** — 좌표가 영역을 벗어나지 않는가,
서로 `minSpacing` 이상 떨어졌는가, 빽빽한 요청에도 끝나는가.
`seed` 를 인자로 받는 이유는 테스트에서 재현하기 위함이다. 게임에서는 매번 다른 값을 넘긴다.

**유닛 오브젝트는 미리 만들어 둔다.** 슬롯을 아군 `Roster.MaxParty`(4) + 적
`BattleField.MaxEnemies`(정하기: 8) 개 만들어 씬에 저장하고, 인원수에 맞춰 켜고 끈다.
런타임 생성은 스프라이트 참조가 씬에 남지 않고 무결성 검사도 볼 수 없다(함정 3.1).

**인카운터의 적 총원이 `MaxEnemies` 를 넘으면 `BuildAll` 이 `LogError` 로 실패시킨다.**
조용히 잘라내면 인스펙터에서 8마리 넘게 적어놓고 왜 안 나오는지 모르게 된다.

## 5. 씬 생성과 검사

### 5.1 `GameBootstrap`

`BuildBattleScene()` 을 추가한다. 농장 씬과 **같은 순서 규칙**을 지킨다 —
`NewScene` 을 에셋을 만지기 전에 부른다(함정 3.9). 씬이 둘이 되므로 `BuildAll` 은
`NewScene → 에셋 → 농장 씬 저장 → NewScene → 전투 씬 저장` 순으로 간다.

**두 번째 `NewScene` 이 다시 참조를 죽인다.** 그래서 전투 씬을 채우기 전에
필요한 에셋을 **경로에서 다시 로드**한다. 이 재로드를 빠뜨리면 8/13 과 똑같은 사고가 난다.

`EditorBuildSettings.scenes` 에 두 씬을 모두 등록한다 — 안 하면 `LoadScene` 이 런타임에 실패한다.

### 5.2 `SceneIntegrityCheck`

지금은 농장 씬만 검사한다. **두 씬을 각각 열어 검사**하도록 바꾼다.
전투 씬에 대해 단언할 것:

- 아군 슬롯 4개 · 적 슬롯 8개가 존재하고, 저장 시점에 **꺼져 있는가**
- 모든 SpriteRenderer / Image 가 **에셋** 스프라이트를 참조하는가
- 버튼 3개(1x · 2x · 나가기)가 리스너를 갖는가
- 체력바 채움 Image 가 슬롯마다 있는가
- `EditorBuildSettings.scenes` 에 두 씬이 등록됐는가

12번 검사(데이터 기반 버튼 개수)는 전투터의 인카운터 버튼 수 == `BattleEncounterDatabase`
크기로 확장한다.

## 6. 테스트

`BattleSimulator` 를 건드리지 않으므로 **기존 122개는 전부 유지된다.**

새로 덮을 순수 로직:

| 대상 | 검증 |
|---|---|
| `PickSpawnPoints` | 영역 안, 최소 간격, 빽빽할 때 종료, 같은 seed → 같은 결과 |
| `BattleHandoff` | 넣고 꺼내면 같은 값, 꺼낸 뒤 비워지는가(재입장 시 유령 방지) |
| `BattleEncounter` 총원 계산 | `entries` 의 `count` 합, 빈 목록 |

uGUI 배치와 연출은 테스트하지 않는다. 씬 배선은 `SceneIntegrityCheck` 가 맡는다.

- **스킬 연출·이펙트·사망 애니메이션** — 지금은 체력바와 로그로만 표현한다

- **실제 아트** — 도형 플레이스홀더 유지

## 8. 미결

### 8.1 전투 진입점 ★여전히 미결

지금은 **상점 건물**이 전투터를 임시로 연다. 전투가 별도 씬이 되면 그 임시 배선을
정리할 기회지만, 어디로 옮길지는 정해지지 않았다.
후보: 건물 5동으로 늘리기 / 필드 바깥 별도 진입점 / 상점 안에 전투 탭.
**상점 착수의 선행 조건이기도 하다.**

### 8.2 `MaxEnemies` 값

8 로 잡아 두었으나 근거가 약하다. 첫 인카운터를 만들어 보고 조정한다.
바꾸면 `BuildAll` 재실행이 필요하다(슬롯이 씬에 고정되므로).

> 구현 후: seed 한 인카운터 셋 중 제일 많은 것이 들쥐 3마리라 8은 아직 여유가 많다.
> 실제로 8을 채우는 인카운터를 만들어 보기 전에는 조정하지 않는다.

### 8.3 배속 단계

1x / 2x 두 단계로 시작한다. 4x 가 필요한지는 실제로 긴 전투를 보고 판단한다.

### 8.4 맵을 몇 개 만들 것인가

`BattleMapData` 구조만 정했고 초기 맵은 하나(들판)만 seed 한다.
맵이 늘어나면 인카운터에서 골라 쓰면 된다.
