# 건물별 개별 씬 — 설계 (2026-08-17)

건물을 클릭하면 패널이 아니라 **건물 안 씬**으로 들어간다.
이번 라운드는 **전달자 + 헛간 한 동**까지다. 나머지 네 동은 같은 자리에 끼운다.

---

## 1. 무엇을 푸는가

지금까지 조작은 전부 `FarmScene` 한 곳에 얹힌 팝업 패널이었다.
건물 안에 들어가는 그림을 원하면 씬이 갈라져야 하는데, **씬이 갈라지는 순간
"저장 버튼을 누르지 않은 진행이 날아가는" 자리가 생긴다.**

이 문제는 이미 한 번 겪었다. 전투 씬을 만들 때 `BattleHandoff` 가 결과에
`GameState` 를 실어 보낸 이유가 정확히 그것이다(2026-08-14 설계 3.3).
**건물이 5동이면 그 자리가 5곳이 된다.** 같은 코드를 다섯 번 적을 수는 없다.

### 이번에 하지 않기로 한 것

- **걸어다니는 내부** — 플레이어가 방 안을 걷고 물건을 클릭하는 방식. 재미있지만
  건물마다 콜라이더·이동·카메라가 새로 필요하다. **정적 화면 + UI** 로 간다(전투 씬과 같은 성격).
- **다섯 동 한 번에** — 한 번에 바꾸면 무엇이 깨졌는지 추적하기 어렵다.
  헛간이 가장 복잡하므로(목록 + 파티 + 육성 진입) **여기서 맞으면 나머지는 반복**이다.

---

## 2. 상태의 이동을 짐에서 떼어낸다

**`SceneHandoff`**(순수 C# 정적)가 `GameState` 를 나른다. `BattleHandoff` 에는
**전투만의 짐**(인카운터·전장·승패·보상·stageId)만 남는다.

| | 나르는 것 | 쓰는 곳 |
|---|---|---|
| `SceneHandoff` | `GameState` + 로그 한 줄 | **모든 씬 전환** |
| `BattleHandoff` | 인카운터·전장 / 승패·보상·stageId | 전투 씬 왕복만 |

**꺼내면 비워진다.** 남겨두면 다음에 그 씬을 열 때 지난 상태가 되살아난다.

### 짐과 상태를 따로 맡기게 두지 않는다

`BattleHandoff.SetRequest/SetResult` 는 상태를 인자로 받아 **`SceneHandoff` 에 함께 맡긴다.**
나눠 두면 호출자가 한쪽을 빠뜨릴 수 있고, 그 실패는
**"돌아와 보니 진행이 날아갔다"** 로만 드러나 원인을 짚기 어렵다.
호출자는 한 번만 부르면 된다.

같은 이유로 `BattleHandoff.Clear()` 는 `SceneHandoff` 도 함께 비운다.
짐만 지우고 상태를 남기면 다음 씬이 지난 상태를 이어받는다.

### 도착한 쪽의 규칙 하나

```
SceneHandoff.TakeState()  →  있으면 그것을 쓴다
                          →  없으면 세이브를 읽는다 (그 씬만 단독 Play 한 경우)
```

`GameRoot.Start` 의 분기가 이 한 줄로 줄었다 — **건물이 늘어도 분기가 늘지 않는다.**
전투 결과는 그 위에 얹는 것이라 순서가 있다: 상태를 먼저 받고, 보상·진행도를 나중에 더한다.

## 3. 왕복은 한 곳에 — `BuildingSceneRoot`

건물 씬의 공통 뼈대를 추상 클래스로 둔다.

- **들어올 때**: 상태를 받고(없으면 세이브 폴백), `EnsureTarget()`, HUD·조율자 바인딩
- **나갈 때**: `ExitToFarm()` — 상태를 그대로 들려 보내고 `FarmScene` 으로

**새 건물 씬은 `DisplayName` 만 적으면 왕복이 끝난다.**
단독 Play 폴백을 둔 이유는 전투 씬이 연습 전투로 시작하는 것과 같다 —
개발 중 그 씬만 여는 일이 잦고, 그때 오류로 죽으면 확인이 느려진다.

### 농장 쪽 진입

`FarmBuilding.sceneName` 이 채워져 있으면 씬으로, 비어 있으면 패널로 간다.
**지금은 헛간만 씬이고 나머지 넷은 패널이다 — 이 공존은 의도된 중간 상태다.**

상태를 들려 보내는 것은 `CareManager.EnterScene` 이 한다.
`FarmBuilding` 은 상태를 모르고, 알 필요도 없다.

## 4. 헛간 화면

포켓몬 PC 박스 구조다.

```
┌────────────────┬──────────────────────────────┐
│  헛간지기 초상  │        보관함  n / 8          │
│                │  ┌──┐┌──┐┌──┐┌──┐            │
│  "고르게…"     │  └──┘└──┘└──┘└──┘            │
│                │  ┌──┐┌──┐┌──┐┌──┐            │
│ 밖에 나가 있는  │  └──┘└──┘└──┘└──┘            │
│ 1. 스프리글링   │                              │
│ 2. (빈 자리)   │      고른 케어 상세            │
│ 3. (빈 자리)   │  [내보내기] [육성] [농장으로]  │
│ 4. (빈 자리)   │                              │
└────────────────┴──────────────────────────────┘
```

- **칸은 8개 고정**(`Roster.MaxMembers`), 파티 줄은 4개 고정(`Roster.MaxParty`).
  런타임 생성 금지 규칙 그대로다(함정 3.1).
- **빈 칸은 감추지 않고 "비어 있음" 으로 보여준다.** 목록과 달리 격자는
  칸이 거기 있다는 것 자체가 정보다.
- **칸을 고르는 것이 곧 육성 대상을 정하는 것이다.** 헛간이 원래 대상을 고르는 곳이고,
  이렇게 해야 창고·상태창이 같은 케어를 가리킨다.
- **인덱스를 들고 있는 것은 칸 버튼뿐이다**(함정 3.6).
  옛 헛간 패널은 줄마다 버튼 두 개가 인덱스를 들었지만,
  격자는 **고르고 → 아래 버튼**이라 조작 버튼이 무인자다.
- 헛간지기 초상은 **자리만 잡은 플레이스홀더**다. 실제 그림은 나중에.

### 방 화면이 `GamePanel` 인 이유

`CareManager` 가 액션 뒤에 다시 그려주는 대상이 `GamePanel` 목록이다.
새 배선을 만들 이유가 없어 그대로 쓴다.

**다만 팝업이 아니다** — 씬의 본체라 **열린 채로 저장**된다.
함정 3.8("패널은 닫아 저장")은 팝업 규칙이고, 헛간 씬에서는 육성 팝업만 그것을 따른다.

### ★ 방과 팝업의 부모를 나눈다

`GamePanel.Open` 은 겹쳐 뜨는 것을 막으려고 **부모 아래의 다른 `GamePanel` 을 전부 끈다.**
한 부모에 두면 `[육성]` 을 누르는 순간 **방이 통째로 꺼져 화면이 검게 변한다.**
예외도 로그도 없다.

→ `RoomRoot` / `PopupRoot` 로 부모를 나눴다. 무결성 검사와 PlayMode 양쪽이 이것을 지킨다.

**일반화: "겹치지 않게 하나만 띄운다"는 팝업의 규칙이다.** 씬의 주 화면이 같은 타입을
재사용하면 그 규칙에 함께 걸린다. 타입이 아니라 **부모로** 갈라야 한다.

## 5. 무엇이 이것을 지키는가

| 검사 | 잡는 것 |
|---|---|
| `SceneHandoffTests`(8) | 꺼내면 비는가 / 같은 객체가 건너가는가 / 로그만 꺼내도 상태가 남는가 |
| `BattleHandoffTests`(11) | 짐과 상태가 함께 맡겨지는가 / `Clear` 가 양쪽을 비우는가 |
| 씬 무결성 검사 | 방은 켜진 채·팝업은 꺼진 채인가 / **부모가 다른가** / 나가는 버튼이 있는가 / 칸 8개·파티 줄 4개 / 헛간 건물의 `sceneName` 문자열 |
| `BarnSceneSmokeTests`(7) | **왕복에 저장 전 진행이 남는가**(제일 중요) / `[육성]` 이 방을 안 꺼뜨리는가 / 파티 변경이 농장 필드에 반영되는가 |

**검사가 실제로 잡는지 확인해 뒀다.** 육성 패널을 `RoomRoot` 밑으로 옮겨 재생성하면
`BuildAll` 은 **종료 코드 0** 으로 성공하지만 무결성 검사가 1 로 실패하고
`RaisingPopup_DoesNotHideTheRoom` 도 함께 실패한다.

## 6. 남은 네 동 (같은 날 이어서 구현)

부화소·창고·상점·전투터는 **기존 패널이 그대로 옮겨갔다.** 행·버튼·문자열·규칙이
하나도 바뀌지 않았고 그릇만 바뀌었다. 헛간처럼 화면을 새로 짜지 않은 이유는,
검증되지 않은 레이아웃을 넷 더 늘리는 것보다 옮기는 쪽이 위험이 훨씬 작기 때문이다.
내부 그림은 실제 아트가 생길 때 각자 짜면 된다.

- **`[닫기]` → `[농장으로]`** (`RewireCloseToExit`). 패널이 씬의 본체가 되면
  닫는다는 개념이 없어진다 — 닫으면 빈 방만 남는다.
- **농장에 패널이 하나도 안 남는다.** 남으면 같은 화면이 두 곳에 있게 되고,
  어느 쪽을 고쳐야 할지 알 수 없다. 무결성 검사가 이것을 단언한다.
- **`NextScene()` 이 "씬 열기 + 참조 되살리기"를 한 함수로 묶는다.** 씬이 늘수록
  함정 3.9 를 밟을 자리가 늘어나므로 빠뜨릴 수 없게 했다.

### 전투 복귀 — 이 라운드에서 유일하게 새로 정한 것

전투터가 씬이 되면서 전투 진입이 **씬 → 씬** 이 됐다. **전투는 들어온 곳으로 돌아온다**
(`BattleRequest.ReturnScene`). 매 전투마다 농장을 거쳐 다시 들어오는 것은 번거롭고,
스테이지를 이어서 고르는 것이 자연스럽다.

**그 대가**: 보상을 새기는 곳이 농장과 전투터 둘이 됐다. "재화·진행도가 늘어나는 지점은
하나"라는 불변조건을 지키려고 규칙을 순수 C# **`BattleReward.Apply`** 로 뺐다 —
**부르는 곳은 둘이어도 규칙은 하나다.** 덤으로 EditMode 테스트가 처음 붙었다.

**남은 거친 면**: 전투터로 돌아오면 화면이 맵 목록부터 다시 시작한다
(`BattlePanel.OnEnable`). 농장을 거치던 것보다는 짧아 그대로 뒀다.

## 7. 다음

**아이템 드랍.** 지급 지점이 `BattleReward.Apply` 하나로 모여 있고
`StageUnlock.RequiresItem` 이 이미 있어, 드랍이 생기면 "열쇠를 먹어야 다음 맵이 열린다"가
코드 수정 없이 된다. 정할 것은 **적/스테이지 중 어디에 붙일지**, **확률을 쓸지**
(쓰면 시뮬레이터가 난수를 안 쓴다는 성질이 깨지므로 전투 밖에서 굴려야 한다),
**결과를 어디에 보여줄지**.
