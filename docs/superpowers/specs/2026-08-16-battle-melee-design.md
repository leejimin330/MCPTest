# 설계 — 위치 기반 전투 (2026-08-16)

**상태:** 설계 승인됨. 구현 전.
**전제:** `2026-08-14-battle-screen-design.md` 에서 이어진다. 그 문서 1.1 이 **"좌표는 표시 전용"**
으로 못 박았고, 덕분에 `BattleSimulator` 와 그 테스트 13개를 한 줄도 건드리지 않고 전투 화면을
만들 수 있었다. **이 문서는 그 결정을 뒤집는다.**

지금 전투는 유닛이 어디에 서 있든 결과가 같다. 스폰은 이미 매번 다르지만
(`BattleSceneRoot.cs` 가 `Random.Range` 로 seed 를 굴려 `SpawnPointPicker` 에 넘긴다)
시뮬레이터가 좌표를 한 번도 읽지 않아 **배치가 승패에 아무 영향을 주지 않는다.**
화면에서 벌어지는 일과 규칙이 따로 논다.

이 문서는 좌표를 규칙으로 끌어올리는 설계다. 유닛이 **가장 가까운 적을 향해 움직이고,
사거리 안에 들면 멈춰 싸운다.** 같은 파티라도 어디에 떨어졌느냐에 따라 이기고 질 수 있다.

> **이 문서의 범위는 교전 방식 하나다.** 같은 날 함께 논의된 두 가지 —
> 전투터에서 맵을 고르고 맵마다 스테이지가 나뉘는 진행 구조, 건물마다 개별 씬을 여는 전환 구조 —
> 는 **별도 프로젝트**로 뺐다. 7절을 본다.

---

## 1. 확정된 결정

| 항목 | 결정 |
|---|---|
| 좌표의 소유자 | **코어.** `BattleUnit` 이 위치를 갖고 `BattleSimulator` 가 갱신한다. 뷰는 읽어 그리기만 한다 |
| 타겟 | **가장 가까운 살아있는 적. 매 틱 다시 판단한다** |
| 이동 중 공격 | **하지 않는다.** 사거리 밖이면 그 틱은 이동만 |
| 스폰 배치 | **난전.** 아군·적 구역을 나누지 않고 한 전장에 섞어 뿌린다 |
| 난수 | **시뮬레이터는 난수를 부르지 않는다.** 스폰 좌표를 생성자 인자로 받는다 |
| 사거리 · 이동속도 | **전 유닛 공통 상수.** 종별 차등 없음 |
| 공격 스킬 사거리 | 평타와 같다 |
| 회복 스킬 사거리 | **무제한** |
| 시간 제한 | **없다.** 무승부를 만들지 않는다 |

### 1.1 왜 "좌표는 표시 전용"을 뒤집는가

그 결정은 전투 화면을 **싸게** 만들기 위한 것이었다. 시뮬레이터를 안 건드리니 테스트 13개가
그대로 살았고, 배속도 한 줄로 얻었다. 대가는 **화면이 거짓말을 한다**는 것이다 — 유닛이
멀리 떨어져 서 있어도 서로를 때리고, 매 전투 배치가 달라져도 결과는 늘 같다.

배치가 결과를 정해야 한다는 요구가 들어온 이상 좌표는 규칙이다. 규칙은 코어에 있어야
EditMode 에서 검증된다(N1). 뷰에 남겨두면 "화면을 띄워야만 확인되는 규칙"이 되고,
이 프로젝트가 반복해서 물린 함정(3.9·3.10)이 정확히 그 자리에서 나온다.

### 1.2 왜 타겟을 매 틱 다시 판단하는가

대안은 "처음 고른 적이 죽을 때까지 문다"였다. 움직임은 안정적이지만, 난전 배치에서
**멀리 있는 상대를 향해 다른 적들을 가로질러 걸어가는** 그림이 나온다. 옆에 적을 두고
지나치는 유닛은 보기에 멍청하다.

매 틱 재판단하면 몰린 쪽이 자연스럽게 집중포화를 맞고, **배치가 결과를 정한다**는
이 작업의 목적이 가장 직접적으로 드러난다. 대가는 적이 다가올 때 타겟이 흔들리는 것인데,
사거리 안에 들면 멈춰서 싸우므로 실제로 흔들리는 구간은 접근 중 잠깐이다.

### 1.3 왜 이동 중에는 때리지 않는가

"일정한 범위에 들어가면 알아서 싸운다"를 그대로 옮긴 것이다. 걸으면서도 때리면
사거리는 "공격이 시작되는 선"이 아니라 "그냥 최대 거리"가 되고, 멈춰 서서 붙는 그림이
사라진다. 접근 → 교전의 리듬이 이 작업이 만들려는 볼거리다.

### 1.4 왜 시간 제한을 두지 않는가

무승부를 만들면 `BattleConclusion` 에 항목이 하나 늘고, 거기 딸려 보상 경로
(`GameRoot.ApplyBattleResult`)와 농장 로그 문구가 함께 는다. 얻는 것에 비해 번진다.

교착이 생길 수 있는가 — 모든 유닛이 가장 가까운 적으로 수렴하므로 **누군가는 반드시
맞는다.** 회복이 피해를 넘어서면 늘어질 수 있지만 그 위험은 지금도 똑같이 있고
(블로섬 가디언의 회복), 실제로 문제가 된 적이 없다. 필요해지면 그때 넣는다.

### 1.5 왜 종별로 사거리를 다르게 주지 않는가

근접·원거리를 나누면 밸런스를 처음부터 다시 잡아야 하고, 종 에셋에 필드가 늘고,
"어떤 진화가 유리한가"가 다시 열린 질문이 된다. 이번 작업의 목적은 **배치가 결과를
정하게 하는 것**이지 병종을 만드는 것이 아니다.

다만 값을 `BattleUnit` 의 필드로 둔다 — 전부 같은 기본값이 들어가지만, 나중에 종별
값을 주고 싶어지면 **데이터만 추가하면 되고 구조는 안 바뀐다.**

## 2. 코어 — `BattleUnit`

세 필드가 는다.

```csharp
/// <summary>전장 좌표. 전투 중에만 존재한다. 생성자가 아니라 시뮬레이터가 배치한다.</summary>
public Vector2 Position;

/// <summary>초당 이동 거리(월드 유닛).</summary>
public float MoveSpeed;

/// <summary>이 거리 안에 들어야 때린다(월드 유닛).</summary>
public float AttackRange;
```

`FromCreature` · `FromEnemy` 는 둘 다 공통 기본값을 넣는다.

```csharp
public const float DefaultMoveSpeed = 2.0f;
public const float DefaultAttackRange = 1.2f;
```

`BattleSimulator` 는 분리 간격의 기본값을 따로 갖는다 — 호출부가 안 넘겼을 때 쓴다.

```csharp
public const float DefaultMinSpacing = 0.9f;   // 사거리(1.2)보다 좁아야 붙어서 때릴 수 있다
```

> **`DefaultMinSpacing` 은 `DefaultAttackRange` 보다 작아야 한다.** 크면 유닛이 사거리 안으로
> 들어가기 전에 서로 밀어내 **영원히 못 때린다.** 값을 바꿀 때 이 관계를 깨지 않는다.

> `Vector2` 는 `UnityEngine` 타입이다. 코어가 `UnityEngine` 에 의존하지 않는다는 N1 은
> **UI·MonoBehaviour 를 두지 않는다**는 뜻으로 지켜져 왔고, `SpawnPointPicker` 가 이미
> `Vector2`·`Rect` 를 코어에서 쓴다(선례). EditMode 테스트는 그대로 돈다.

## 3. 코어 — `BattleSimulator`

### 3.1 생성자가 좌표를 받는다

```csharp
public BattleSimulator(
    IList<CreatureInstance> party,
    IList<EnemyData> foes,
    IList<Vector2> allyPositions,
    IList<Vector2> enemyPositions,
    float minSpacing = DefaultMinSpacing)
```

`minSpacing` 은 겹침을 막는 데만 쓴다(4절). 맵마다 다를 수 있어 인자로 받는다 —
`BattleSceneRoot` 가 `BattleMapData.minSpacing` 을 그대로 넘긴다. **코어가 `BattleMapData` 를
알지 못하게** 하려고 데이터가 아니라 값을 받는다. 0 이하면 분리를 끄고 겹치게 둔다.

**시뮬레이터 안에서 난수를 부르지 않는다.** 배치를 고르는 일은 바깥(`BattleSceneRoot`)이 하고,
시뮬레이터는 받은 좌표를 그대로 쓴다. 그래서

- 게임: 매 전투 다른 좌표 → **다른 결과** (이 작업이 원하는 것)
- 테스트: 좌표를 손으로 놓음 → **완전히 결정적** (기존 13개가 산다)
- 시뮬레이터: 여전히 난수 없음 — "같은 입력이면 같은 결과"라는 성질은 그대로다

좌표 목록이 유닛 수보다 짧으면 남는 유닛은 `Vector2.zero` 에 선다. 짧은 목록은 호출부의
실수지만 예외로 죽이지 않는다 — 전투가 안 열리는 것보다 겹쳐 서는 편이 낫다.

### 3.2 틱

```
Tick(dt):
    ElapsedSeconds += dt
    Advance(아군, 적, dt)      ← 순서 고정: 재현성
    Advance(적, 아군, dt)
    Outcome = Resolve()

Advance(side, opponents, dt):
    각 살아있는 unit 에 대해:
        target = NearestAlive(opponents, unit.Position)     ← 매 틱 재판단
        if target == null: continue

        거리 = |target.Position − unit.Position|

        if 거리 > unit.AttackRange:
            unit.Position += (방향(target) * unit.MoveSpeed + 분리(unit)) * dt   ← 4절
            타이머만 흐르고 공격은 하지 않는다
        else:
            멈춘다. 스킬 타이머 · 평타 타이머를 돌려 지금처럼 행동한다
```

**타이머는 이동 중에도 찬다.** 그래야 붙는 순간 평타·스킬이 바로 나가고, 접근 시간이
공백으로 느껴지지 않는다. 무한히 쌓이는 것은 기존 `MaxActionsPerTickPerUnit`(8) 이 막는다.

### 3.3 타겟 선택

```csharp
private static BattleUnit NearestAlive(List<BattleUnit> units, Vector2 from)
```

거리가 같으면 **목록에서 앞선 쪽**을 고른다. 동률에 순서를 못 박아야 결과가 재현된다.

### 3.4 스킬

| 스킬 | 사거리 | 대상 |
|---|---|---|
| `SkillEffect.Damage` | 평타와 같다. 사거리 밖이면 나가지 않는다 | 지금 노리는 그 타겟 (가장 가까운 적) |
| `SkillEffect.Heal` | **무제한** | 지금처럼 체력 **비율**이 가장 낮은 아군 |

회복만 거리를 무시하는 이유: 난전에서 회복이 사거리에 걸리면 옆에 아군이 있을 때만
터져 뿔뿔이 흔들린다. 블로섬 가디언은 **회복이 존재 이유인 진화 분기**라
(스프리글링 → 블룸 스톤 장착 경로), 거리 운에 값어치를 맡기면 분기 자체가 흐려진다.

공격 스킬이 타겟을 평타와 공유하는 것도 같은 이유다 — 스킬만 다른 적을 노리면
"가장 가까운 적을 때린다"는 규칙이 유닛마다 둘로 갈린다.

## 4. 겹침 — 최소한만 막는다

난전이고 모두가 가장 가까운 적으로 수렴하므로 한 점에 몰린다. 사거리에서 멈추니 어느 정도는
자연히 벌어지지만, 같은 적을 노리는 유닛들은 그 적 위에 포개진다.

**규칙 하나만 둔다.** 이동할 때, 다른 살아있는 유닛(아군·적 가리지 않음)과
`minSpacing` 보다 가까우면 그 유닛 반대 방향으로 밀린다.

```
겹침(other) = minSpacing − |unit.Position − other.Position|      // 양수일 때만
분리(unit)  = Σ (unit.Position − other.Position).normalized × 겹침(other)

이동 = 타겟방향 × MoveSpeed × dt  +  분리(unit) × dt
```

**밀어내기도 `dt` 로 스케일한다.** 안 그러면 한 틱의 이동량이 틱 길이에 비례하지 않아,
프레임률이 흔들리는 것만으로 유닛이 더 멀리 밀린다.

> **주의 — 이것으로 틱 크기 독립성까지 얻지는 못한다.** 밀어내는 힘이 위치에 의존하므로
> `Tick(1.0)` 한 번과 `Tick(0.1)` 열 번은 **원리상 결과가 다르다**(오일러 적분 오차).
> 3.1 이 보장하는 것은 **같은 좌표 + 같은 틱 열이면 같은 결과**이지, 틱을 어떻게 쪼개도
> 같다는 것이 아니다. 게임은 `Time.deltaTime` 을 그대로 넘기므로 프레임률이 결과에 영향을 준다 —
> 대전이나 리플레이가 없어 지금은 문제되지 않지만, 생기면 고정 틱으로 바꿔야 한다.

두 유닛이 정확히 같은 좌표에 있으면 방향이 정해지지 않는다(`normalized` 가 0 벡터).
이때는 **밀지 않는다** — 임의 방향을 지어내면 그 선택이 곧 숨은 난수가 된다.
6.1 의 테스트가 정확히 이 경우다.

물리 엔진을 쓰지 않는다. 밀어내기는 **이동하는 유닛에만** 적용된다 — 이미 멈춰 싸우는
유닛까지 밀면 사거리 안팎을 오가며 떨리게 된다.

> 완벽한 분리는 목표가 아니다. HANDOFF 8절의 "유닛이 서로 겹쳐 보이지 않고"를
> 읽을 만한 수준으로 만드는 것까지다.

## 5. 스폰 — 맵 에셋을 건드리지 않는다

`BattleMapData` 는 `AllySpawnArea` 와 `EnemySpawnArea` 를 따로 들고 있고, **seed-only 에셋**이라
(함정 3.11) 코드에서 초기값을 바꿔도 이미 있는 4개 맵(`FieldMap`·`RatField`·`BoarThicket`·
`GolemRidge`)에는 반영되지 않는다. 반영시키려면 `.asset` 을 지워야 한다.

**지우지 않는다.** 맵 데이터 구조는 7절의 별도 프로젝트(맵/스테이지)에서 어차피 다시 짠다.
여기서 한 번 갈아엎고 거기서 또 갈아엎을 이유가 없다.

→ `BattleSceneRoot` 가 **두 영역을 감싸는 사각형**을 계산해 전장으로 쓴다.

```csharp
Rect battlefield = Rect.MinMaxRect(
    Mathf.Min(map.AllySpawnArea.xMin, map.EnemySpawnArea.xMin),
    Mathf.Min(map.AllySpawnArea.yMin, map.EnemySpawnArea.yMin),
    Mathf.Max(map.AllySpawnArea.xMax, map.EnemySpawnArea.xMax),
    Mathf.Max(map.AllySpawnArea.yMax, map.EnemySpawnArea.yMax));
```

아군과 적을 **한 번의 `PickSpawnPoints` 호출로 함께** 뽑는다. 두 번 나눠 뽑으면 서로의
간격이 보장되지 않아 아군 위에 적이 겹쳐 설 수 있다. 뽑은 목록의 앞쪽 `party.Count` 개를
아군에, 나머지를 적에 준다.

`SpawnPointPicker` 는 **한 줄도 바뀌지 않는다.** 이미 하나의 `Rect` 안에서 최소 간격을
지켜 뽑고, 자리를 못 찾으면 격자로 물러난다.

seed 는 지금처럼 `BattleSceneRoot` 가 `Random.Range` 로 굴린다 — 매 전투 배치가 달라야 하고,
이제 그것이 결과까지 바꾼다.

## 6. 검증

### 6.1 기존 `BattleSimulatorTests` 13개는 유지한다

생성자가 좌표를 받게 되니 전부 손이 가지만, **단언은 하나도 안 바뀐다.**
셋업에서 **모든 유닛을 서로의 사거리 안에 붙여 놓으면** 이동 구간이 사라져
지금과 똑같이 동작한다.

```csharp
// 헬퍼 하나로 13개를 살린다
private static List<Vector2> Clustered(int count)
{
    var points = new List<Vector2>();
    for (int i = 0; i < count; i++) { points.Add(Vector2.zero); }
    return points;
}
```

전부 `Vector2.zero` 면 거리 0 이라 항상 사거리 안이다. 이동하지 않으므로 분리 규칙도
적용되지 않고(4절), 좌표가 같아 밀 방향도 없다.

**단언이 하나도 안 바뀌는 진짜 이유는 타겟 선택이 같아지기 때문이다.** 모두가 거리 0 이면
`NearestAlive` 는 동률이 되고, 동률은 목록 순서로 깨진다(3.3) — 즉 **지금의
`FirstAlive(opponents)` 와 정확히 같은 유닛을 고른다.** 피해량·순서·로그가 전부 그대로다.

이것이 성립하지 않으면(예: 동률을 다른 방식으로 깨면) 13개 중 상당수가 깨진다.
**Task 순서상 이 헬퍼를 먼저 넣어 13개가 초록인 것을 확인한 뒤에** 새 동작을 얹는다.

### 6.2 새 테스트 — `BattleSimulatorTests` 에 더한다

| 테스트 | 단언 |
|---|---|
| `사거리 밖이면 때리지 않는다` | 멀리 떨어뜨려 한 틱 굴리면 **아무도 체력이 안 준다** |
| `걸어가서 붙는다` | 여러 틱 굴리면 거리가 `AttackRange` 이하로 줄고, 그 뒤 체력이 준다 |
| `가장 가까운 적을 노린다` | 적 둘을 두고 가까운 쪽만 맞는다 |
| `적이 다가오면 타겟이 바뀐다` | 매 틱 재판단이 실제로 도는가 |
| `회복은 거리를 무시한다` | 회복 유닛을 멀리 떼어놔도 아군이 회복된다 |
| `공격 스킬은 사거리를 지킨다` | 쿨다운이 다 차도 사거리 밖이면 안 나간다 |
| `같은 좌표면 같은 결과` | 같은 입력·같은 좌표로 두 번 굴려 로그와 결과가 동일 |
| `다른 좌표면 결과가 갈릴 수 있다` | 배치를 바꾸면 승패가 뒤집히는 사례가 **실재함**을 고정 |
| `한 틱 이동량이 dt 에 정비례` | 같은 상태에서 `Tick(0.2)` 의 이동량이 `Tick(0.1)` 의 정확히 두 배다. 분리를 `dt` 로 안 곱하면 그 성분이 두 배가 되지 않아 걸린다 |
| `분리 간격이 사거리보다 좁다` | `DefaultMinSpacing < DefaultAttackRange`. 뒤집히면 아무도 못 때린다 (2절) |

마지막 둘이 이 작업의 핵심 단언이다. 앞의 것이 없으면 결정성이 깨진 것을 못 잡고,
뒤의 것이 없으면 **좌표가 정말 결과를 정하는지** 아무도 확인하지 않은 채로 끝난다.

### 6.3 `SpawnPointPickerTests` 7개 — 건드리지 않는다

`SpawnPointPicker` 가 안 바뀌므로 그대로 통과해야 한다. 통과하지 않으면 안 건드리기로 한
것을 건드린 것이다.

### 6.4 PlayMode 스모크 7개

**"체력바가 실제로 줄어든다"가 늦어질 수 있다** — 이제 붙기까지 시간이 걸린다.
`Time.timeScale = 10` 으로 압축하고 있어 통과할 가능성이 높지만, **확인 없이 통과를
가정하지 않는다.** 실패하면 굴리는 시간을 늘린다(단언을 약하게 만들지 않는다).

"유닛이 스폰 영역 안에 선다"는 단언도 본다 — 이제 유닛이 **움직이므로** 영역 안이라는
보장이 시작 시점에만 성립한다. 스폰 직후에 재도록 옮기거나, 전장 사각형 기준으로 고친다.

### 6.5 씬 무결성 검사

전투 씬 구조가 안 바뀌므로 **검사도 안 바뀐다.** 슬롯 개수·배선·버튼은 그대로다.

## 7. 범위 밖

같은 날 논의됐지만 **이 문서에 들어오지 않는 것들.** 각각 자기 설계 문서를 갖는다.

- **맵 선택과 스테이지 진행** — 전투터에 들어가면 맵을 고르고, 맵마다 스테이지가 나뉜다.
  `BattleEncounter`/`BattleEncounterDatabase` 계통 재구성 + 진행도 저장(세이브 v3 변경 가능성).
- **건물마다 개별 씬** — 지금은 `FarmScene` 한 곳에 패널 6종이 얹혀 있다.
  씬으로 쪼개면 씬마다 생성·무결성 검사·상태 인계가 각각 필요하다.

**이 둘은 서로 겹친다** — 전투터가 개별 씬이 되면 그 씬이 곧 맵 선택 화면이다.
따로 만들면 같은 화면을 두 번 만들게 되므로 **한 프로젝트로 묶어 설계한다.**

그 밖에: 종별 사거리·이동속도(1.5), 시간 제한과 무승부(1.4), 원거리 병종,
지형·장애물, 유닛 조작.

## 8. 남는 위험

**밸런스가 흔들린다.** 피해 공식(`공격 − 방어/2`)과 적 3종의 수치는 "모두가 즉시 서로를
때린다"를 전제로 맞춰진 값이다(HANDOFF 4.5 에서 이미 "검증된 곡선이 아니다"라고 적었다).
접근 시간이 생기고 집중포화가 배치에 따라 갈리면 체감 난이도가 달라진다.
**이번 작업에서 수치는 건드리지 않는다** — 먼저 돌려보고, 필요하면 별도로 잡는다.

**진화 분기의 값어치가 달라질 수 있다.** 회복(블로섬 가디언)은 사거리를 무시하므로 그대로지만,
공격 스킬(와일드비스트)은 사거리에 걸린다. 접근이 느린 상황에서 상대적으로 손해다.
`WildbeastPath_IsGatedByExpNotAttack` 은 진화 시점만 고정하므로 영향받지 않지만,
"어느 진화가 센가"는 다시 열린 질문이 된다.

**"매번 다른 결과"가 불평의 씨앗이 될 수 있다.** 같은 파티로 같은 상대에게 졌다 이겼다 하면
플레이어는 자기가 뭘 했는지 모른다. 지금은 져도 잃는 게 없어(부상·사망 없음) 부담이 적지만,
스테이지 진행(7절)이 들어오면 다시 볼 것.
